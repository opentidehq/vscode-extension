# Architecture

How the extension is put together, and how a feature plugs in. Read this and [`SPEC.md`](SPEC.md); the
cross-repository interfaces are [`CONTRACTS.md`](CONTRACTS.md).

## Layout

```text
package.json            manifest; `contributes` and `activationEvents` are GENERATED (npm run manifest)
contrib/                manifest fragments: core.json, grammars.json (generated), <feature>.json
pins.json               bundled opentide, CPython, highlights zip (+SHA-256), runtime targets and archives, VSIX size budget
runtime/                requirements.in and locks/<target>.txt (committed); the built runtime (not committed), see PACKAGING.md
src/extension.ts        activate(): the core, then every feature (a virtual workspace gets src/web/ instead)
src/web/                the `browser` entry (vscode.dev, github.dev): grammar-only mode, no Node built-ins
src/core/               the core (below); vscode-free modules unless under core/services/ or core/webview/panel.ts
src/features/<id>/      one folder per feature; index.ts default-exports defineFeature(...)
src/features/index.generated.ts   generated by scripts/features-index.mjs (not committed)
webview/<name>/main.ts  a webview entry, bundled to dist/webview/<name>.js
webview/shared/         base.css (theme variables) and channel.ts (the webview end of the message channel)
syntaxes/               TextMate grammars, copied by scripts/grammars.mjs (never hand-written)
language-configuration/ comment tokens, brackets and pairs per language (hand-written)
scripts/                manifest.mjs, features-index.mjs, grammars.mjs, build.mjs, release.mjs, runtime-lock.mjs,
                        runtime-build.mjs, package.mjs, smoke.mjs (+ *-lib.mjs, tested)
.github/workflows/      ci.yml (every PR and push to main), publish.yml (releases: docs/RELEASING.md)
test/unit/              mocha in plain node (npm test); test/stubs/vscode.ts stands in for `vscode`
test/scripts/           tests of scripts/*.mjs
test/integration/       @vscode/test-cli, label `integration` (needs a VS Code download)
test/restricted/        @vscode/test-cli, label `restricted` (Restricted Mode)
test/fixtures/          fake-opentide.mjs (CLI and `serve`), commands-0.20.1.json, a workspace
```

## Activation

`activate()` creates the core (services, core commands, status items) synchronously, calls every
feature's `activate(ctx)`, then starts the runtime resolution and the language server in the
background. Nothing on that path starts a process (SPEC §14: activation < 300 ms).

- Features activate **in parallel and isolated**: one that throws or rejects is logged to the
  `opentide` output channel and the rest carry on.
- `activate(ctx)` runs **before** the first runtime resolution finishes. Subscribe to events
  synchronously in `activate` and read `.current` when an event fires; never assume a runtime exists.
- Features activate in **Restricted Mode too**. The backend refuses to run there (`untrusted`); show
  "Trust this folder…" states instead of commands (`when` clause `isWorkspaceTrusted`).
- **Web and virtual workspaces** (vscode.dev, github.dev, Remote Repositories) run `src/web/extension.ts`
  instead: no core and no feature activates. Languages, grammars and language configuration are
  declarative and still work; a language status item says "Highlighting only", and every contributed
  command answers with an explanation instead of "command not found". Hide what needs a runtime with
  `opentide.runtimeReady` (never set there) or `!isWeb` in `when` clauses. The web bundle must not import
  `src/core/` or a Node built-in (`test/scripts/web-bundle.test.mjs`).

## How to add a feature

1. **Code:** `src/features/<id>/index.ts` (`<id>` is kebab-case and equals the folder name):

   ```ts
   import * as vscode from "vscode";
   import { defineFeature } from "../../core/feature";

   export default defineFeature({
     id: "explain",
     activate(ctx) {
       ctx.subscriptions.push(
         vscode.commands.registerCommand("opentide.explain.code", async (code: string) => {
           const folder = await ctx.folders.pick();
           if (!folder) return;
           const result = await ctx.backend.run(folder.path, ["explain", code]);
           // result.document is exactly what `opentide --json explain <code>` prints
         }),
       );
     },
   });
   ```

   Put logic in vscode-free modules next to it (`src/features/<id>/model.ts`) so it is unit-tested in
   plain node; keep `index.ts` as thin glue.
2. **Manifest:** `contrib/<id>.json` holds only `activationEvents` and `contributes`:

   ```json
   {
     "contributes": {
       "commands": [{ "command": "opentide.explain.code", "title": "Explain a Code…", "category": "opentide" }],
       "configuration": { "title": "opentide: Explain", "properties": { "opentide.explain.preview": { "type": "boolean", "default": true } } }
     }
   }
   ```

   Then `npm run manifest` rewrites `package.json`. **Never hand-edit `contributes` or
   `activationEvents` in package.json**; CI runs `npm run manifest:check`. The merge fails on a
   duplicate command id, setting key, view id, view container id or walkthrough id, and on two
   fragments giving the same scalar different values. Arrays concatenate (core first, then fragments
   by file name); objects merge.
3. **Names:** commands `opentide.<id>.<action>`, settings `opentide.<id>.*`, views `opentide.<id>…`,
   context keys `opentide.<id>.*`, webview view types `opentide.<id>`. Restricted settings (those a
   workspace must not set) are listed in package.json `capabilities.untrustedWorkspaces`: the core
   already lists `opentide.mcp.provide` and `opentide.terminal.addToPath`; adding another is a core change.
4. **Views:** the activity bar container `opentide` is the core's; add views to
   `contributes.views.opentide`. Use `viewsWelcome` with `opentide.trusted`, `opentide.hasWorkspace`
   and `opentide.hasCli` for the empty and Restricted Mode states.
5. **Webviews:** `webview/<id>/main.ts`; `npm run build` finds it. See [Webviews](#webviews).
6. **Tests:** `test/unit/<id>/*.test.ts` (mocha, plain node), and an integration skeleton in
   `test/integration/<id>.test.ts` where the behaviour needs VS Code.
7. **Docs:** a bullet under `## [Unreleased]` in CHANGELOG.md and the feature's README section. If two
   branches add bullets at the same spot, keep both.

When two branches change `package.json` contributes, resolve the conflict by taking either side and
running `npm run manifest`: the fragments are the source of truth.

## The FeatureContext

`ctx` (`src/core/context.ts`). Every event is a `vscode.Event`-compatible function.

### `ctx.log`

The `opentide` LogOutputChannel: `trace`, `debug`, `info`, `warn`, `error`, `show()`. No secrets: the
backend already logs every run (command line with secrets redacted, folder, duration, exit code,
`failure.code`).

### `ctx.runtime`

| Member | |
|--------|-|
| `current: Runtime \| undefined` | The resolved runtime (`src/core/runtime/types.ts`): `tier` 1–4, `source`, `kind` (`opentide` or a bare `opentide-lsp`), `command`, `args`, `version`, `interpreter`, `restricted`, `binDirs` |
| `attempts` | How each tier answered (for diagnostics UIs) |
| `pin` | The repository's exact opentide pin (`uv.lock`, `requirements*.txt`, `pyproject.toml`), if any |
| `onDidChange` | After every resolution |
| `ready()` | The first resolution |
| `restart(reason)` | Re-resolve and restart the language server and the backend ("opentide: Restart Server") |

Tiers (SPEC §4): 1 `opentide.path`; 2 the workspace environment (`opentide.interpreter`, else Python
Environments, else the Python extension, else `.venv`, else `PATH`); 3 `uv tool run --from
opentide==<pin>`, only with `opentide.uv.usePin` (then tried before tier 2); 4 the bundled
`<extension>/runtime` (`python -I -X utf8 -X pycache_prefix=<globalStorage>/pycache -m opentide`; tiers 1–3 get
`PYTHONUTF8=1` and `PYTHONIOENCODING=utf-8` in their `env`; built as
[PACKAGING.md](PACKAGING.md) says). The first time tier 4 runs, after the language server starts, the
core compiles the runtime's bytecode into that prefix in the background (`src/core/runtime/precompile.ts`:
`compileall -q`, low priority, cancelled on deactivation, once per `runtime/BUILD-INFO.json` `buildId`;
the bytecode of builds whose runtime folder is gone is deleted). A tier older
than `MIN_OPENTIDE_VERSION` (`src/core/runtime/version.ts`) is refused with its upgrade command, except
an untagged dev build (`0.1.devN+g<sha>`, what hatch-vcs reports for a checkout with no release tag), which
cannot be ordered and is used with a note in the output channel. In
Restricted Mode only tier 4 resolves, `restricted: true`, and its processes get `PATH` = the runtime's
`bin` only.

To start opentide yourself (a terminal, a task, an MCP server definition), use the runtime as it is:
`cliCommand(runtime, ["mcp", "start"])` gives `{ command, args }` (the bundled runtime's command is its
interpreter with `-I … -m opentide`), and `processEnv(process.env, runtime, process.platform, extra)`
its environment (`src/core/runtime/types.ts`, `src/core/runtime/env.ts`). `runtime.binDirs` are the
folders to prepend to a terminal's `PATH`.

### `ctx.backend`

```ts
run(folder: string, argv: string[], options?: {
  cancellation?: vscode.CancellationToken;
  credentials?: boolean;      // default: only when the command contacts a tenant
  onProgress?: (event: ProgressEvent) => void;
  via?: "auto" | "spawn";     // force a process of its own
  env?: Record<string, string>;
}): Promise<{ document, exitCode, argvDisplay, folder, durationMs, via, cancelled }>
```

- `argv` is what follows `opentide` without `--json`: `["validate", "--file", path]`.
- `document` is exactly what `opentide --json <argv>` prints, envelope included
  (`src/core/backend/types.ts`: `ok`, `status`, `message`, `exit_code`, `summary`, `failure`, …).
  **A command failure resolves** with its document; read `exitCode` and `document.failure.code`.
- It **rejects** with a `BackendError` (`code`) only when no document came back: `no-runtime`,
  `untrusted` (Restricted Mode), `editor-only` (bare `opentide-lsp`), `spawn-failed`, `bad-output`,
  `crashed`, `protocol`, `disposed`. Check `ctx.backend.availability()` first to show a state instead.
- `argvDisplay` (`opentide --json …`, shell-quoted, secrets redacted) is what the UI shows and copies (P3).
- **Routing:** `opentide serve` (one warm process per window, CONTRACTS.md) when the active opentide's
  tree has `serve` and `opentide.backend.serve` is `auto`; otherwise, and for commands classified
  `spawn` (setup, generate, query, deploy, doctor, migrate), `opentide --json <argv>` as its own process.
  A serve that dies under a read-only request is restarted and the request retried once.
- **Concurrency:** commands classified as writing run one at a time, in order; read-only ones run
  concurrently.
- **Environment:** `OPENTIDE_REPO_ROOT=<folder>`, `NO_COLOR=1`, `http.proxy` as `OPENTIDE_PROXY`,
  `OPENTIDE_PROGRESS=json` with `onProgress`; credentials (SecretStorage, then `opentide.envFile`
  underneath) only for tenant-contacting runs.
- **Cancellation:** `$/cancelRequest` under serve; SIGINT on POSIX; a process-tree kill on Windows. A
  cancelled run resolves with exit code 130 and `cancelled: true`.
- `onDidRun` fires when a run starts (`status: "running"`) and ends (`ok`, `failed`, `cancelled`,
  `error`). After a writing command the core refreshes that folder's catalogue.
- `invalidate(paths)` is done for you: the core forwards object and `.opentide/` file events.
- `credentialEnv(folder)`: the variables a tenant-contacting run gets (SecretStorage over
  `opentide.envFile`), for a process the extension starts itself, such as a task or a terminal running
  `query`. Empty when commands cannot run. Never log or show the values.

### `ctx.capabilities`

The active opentide's `opentide --json commands`, read once per version (cached under global storage).
**Never compare version numbers**; ask:

| Member | |
|--------|-|
| `hasCommand("info catalog")` | A command path, or a command plus a value of its first positional argument's choices |
| `hasOption("lint", "--file")` | An option of that command, or a global option |
| `commands()` | Every `CommandInfo` (path, summary, arguments, options, `output_schema`) |
| `classify(argv)` | `{ class, writes, contactsTenant, spawn }`; `class` is `read-only`, `writes-workspace`, `contacts-tenant`, `deploys` or `shares` (SPEC §11) |
| `registerClassifier(fn)` | Answer before the built-in table (`src/core/capabilities/classification.ts`) |
| `current`, `ready()`, `onDidChange` | The `CommandTree`, once loaded |

The built-in table classifies every command of the pinned opentide; `test/unit/capabilities.test.ts`
fails when one is missing. An unknown command is `unclassified: true`: queued as a writer, never given
credentials. A feature that needs a command the active opentide lacks shows what is needed (the command
path) instead of failing.

### `ctx.client`

The window's one `LanguageClient` (vscode-languageclient 10): `current`, `ready()`, `onDidChange`, and
`serverInfo` = `capabilities.experimental.opentide` from `initialize` (`host`, `engine`, `catalog`,
`configurationChecks`, `configurationSchemas`), undefined when the server sends none. Pulled
diagnostics are on and the server's refresh requests are honoured by the client. **Add no middleware
that handles `publishDiagnostics`**; the `opentide` diagnostic collection is the server's. Use
`client.sendRequest` for server requests (`opentide/compiledKql`, `workspace/symbol`, …). The core
registers `opentide.showReferences` for the reference lens.

### `ctx.catalog`

One `info catalog` document per folder (CONTRACTS.md; types in `src/core/catalog/types.ts`).

| Member | |
|--------|-|
| `get(folder)` | `CatalogState`; the first call starts loading |
| `refresh(folder, {immediate?})` | Debounced 1 s, single-flight; resolves after a refresh that started after the call |
| `onDidChange` | A folder's state changed |

`CatalogState.status`: `empty`, `loading`, `ready` (`catalog`), `unavailable` (`unavailable.reason`:
`untrusted`, `no-runtime`, `editor-only`, or `needs-command` with `unavailable.command = "info
catalog"`), `error` (`error`; the last good `catalog` is kept). Without a catalogue, `symbols` holds
names and locations from the language server's `workspace/symbol`. The core refreshes on object and
`.opentide/` file events, after writing commands, and after a runtime change.

### `ctx.activity`

The last 50 runs, newest first: `list()`, `onDidChange`, `clear()`. Each entry: `argv`, `argvDisplay`,
`folder`, `startedAt`, `status`, `via`, `durationMs`, `exitCode`, `failureCode`, `error`.

### `ctx.credentials`

Tenant credentials in SecretStorage, **per workspace folder, keyed by the variable name** the
platform TOML names: `set(folder, name, value)`, `get`, `has`, `delete`, `names(folder)`,
`env(folder)`, `onDidChange`. Never written to a file, never sent to a webview, never logged.

### `ctx.trust`

`isTrusted`, `onDidGrant` (fired after the core has restarted on the best tier).

### `ctx.folders`

Workspace folders that contain `.opentide/` or `objects/`: `all` (`{ folder, path, objectFolders }`,
object folders from `paths.toml`), `onDidChange`, `folderOf(uri)`, `pick()` (the active editor's
folder, else the only one, else a quick pick), `isObjectFile(uri)`.

### `ctx.status`

`setCounts(source, { errors, warnings })` (the status bar shows the sum over sources; pass
`undefined` to clear) and `addMenuItem({ label, command, args?, order? })` for the status item's menu
(core items: Show output 100, Restart server 110, Switch runtime 120).

### `ctx.positions`

CLI positions are 1-based with columns in Unicode code points; VS Code's are 0-based UTF-16.
`toPosition(document, line, column?)` and `toRange(document, { line, column?, end_line?, end_column? })`
convert against the document's text (a finding without a column covers its line). The pure functions
are in `src/core/positions.ts`.

### `ctx.onDidChangeFiles`

`{ folder, uris }` batches of created, changed and deleted files under the object folders and
`.opentide/` (not `.opentide/exports/` or `.opentide/lsp/`), 300 ms after the last event.

### Context keys

`opentide.trusted`, `opentide.hasWorkspace`, `opentide.runtimeReady`, `opentide.hasCli` (a trusted
opentide runtime), `opentide.runtimeTier`, `opentide.pinMismatch`, `opentide.serveRunning` (the warm backend runs), and
`opentide.hasInfoCatalog` (the active opentide's command tree has `info catalog`, updated whenever the tree
changes).

## Webviews

`ctx.webview.createPanel({ viewType, title, entry, validators, column?, retainContextWhenHidden? })`
opens a panel on `dist/webview/<entry>.js` with:

- a CSP of `default-src 'none'`, scripts only with a per-page nonce, styles and images only from the
  extension; `localResourceRoots` = `dist/webview`;
- `dist/webview/base.css`, theme variables only (light, dark, high contrast);
- a typed channel. Declare the protocol once in a file both sides import (no `vscode`, no DOM):

  ```ts
  import { is, type Protocol, type Validators } from "../../src/core/webview/protocol";
  export interface GraphProtocol extends Protocol {
    toWebview: { data: GraphData };
    toHost: { open: string; ready: undefined };
  }
  export const hostValidators: Validators<GraphProtocol["toHost"]> = { open: is.string, ready: is.nothing };
  ```

  Host: `panel.channel.post("data", …)`, `panel.channel.on("open", uuid => …)`. Webview:
  `createChannel<GraphProtocol>(webviewValidators)` from `webview/shared/channel.ts`. Messages that
  fail validation are dropped on both sides.

A page's own styles go in a `<style>` element carrying the page's nonce
(`(document.currentScript as HTMLScriptElement).nonce`); the CSP allows no other inline style, while
setting `element.style` from script is fine.

For a `WebviewView`, use `ctx.webview.webviewOptions()`, `ctx.webview.html(webview, entry, title)` and
`ctx.webview.connect(webview, validators)`. A webview never receives a secret, and every action goes
through the host.

## Rules

- **P3:** every action is a real opentide command through `ctx.backend`; show `argvDisplay`.
- **D3:** the UI never writes workspace files itself; opentide commands or text edits the user applies do.
- No telemetry. No `console.log` (lint fails): use `ctx.log`.
- No process on the activation path; start work in the background and show progress.
- Read restricted settings only through `readRestricted` (`src/core/services/settings.ts`), which
  returns undefined in Restricted Mode without reading them.
- Feature-detect newer VS Code APIs (`engines.vscode` is the floor of vscode-languageclient,
  `@types/vscode` matches it): `if ("registerMcpServerDefinitionProvider" in vscode.lm)`.

## Build and test

| Command | |
|---------|-|
| `npm run build` | esbuild: `dist/extension.js`, `dist/web/extension.js` (the `browser` entry), `dist/webview/*.js`, `dist/webview/base.css`, `dist/THIRD-PARTY-NOTICES.txt` (every npm package bundled into the extension, the web entry or a webview) |
| `npm run typecheck` | tsc (strict) over src and test, and over webview/ with the DOM |
| `npm run lint` | Biome (lint and format check); `npm run format` fixes |
| `npm test` | tsc to `out/`, then mocha: test/unit and test/scripts in plain node |
| `npm run manifest` / `manifest:check` | package.json from contrib/*.json |
| `npm run grammars` / `grammars:check` | syntaxes/ and contrib/grammars.json from the pinned zip (SHA-256 checked) |
| `npm run test:integration`, `test:restricted` | @vscode/test-cli labels (download VS Code) |
| `npm run runtime:lock` / `-- --check` | runtime/locks/<target>.txt from runtime/requirements.in (pins.json) |
| `npm run runtime:build -- --target <t>` | runtime/ for one target: interpreter, closure, BUILD-INFO, SBOM, notices |
| `npm run package -- --target <t>` / `-- --universal` | dist-vsix/opentide-<t>-<version>.vsix (+ `.size.json`), size gate |
| `npm run smoke -- <vsix>` | runs the package's bundled opentide (`--version`, `doctor --offline`, LSP `initialize`) |
| `npx @vscode/vsce package` | a VSIX of the working tree (use `npm run package -- --universal` for the universal one) |
| `node scripts/release.mjs <command>` | release helpers for publish.yml: `version`, `check`, `notes`, `matrix`, `assets`, `sums`, `sizes` ([RELEASING.md](RELEASING.md)) |

Unit tests import vscode-free modules directly. A module that touches a little of the VS Code API
loads against `test/stubs/vscode.ts` (registered by `.mocharc.json`); extend the stub when needed, and
keep it to behaviour VS Code has. `test/fixtures/fake-opentide.mjs` is a fake opentide (`--version`,
`--json <command>` and `serve` per CONTRACTS.md); `fakeRuntime()` in `test/unit/helpers.ts` runs it.
Tests against a real opentide run when `OPENTIDE_TEST_BIN` and `OPENTIDE_TEST_WORKSPACE` are set.
