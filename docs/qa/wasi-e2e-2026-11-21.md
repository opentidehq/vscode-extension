## Verdict

- **VS Code, #82: passes** the install, editor features, serve features, MCP (direct), Restricted Mode and
  robustness steps. Small defects found (issues #87–#92); none blocks the flow.
- **VS Code, #83: the bridge works.** On the first module (`8b55d0c`) its tenant path could only be proven against a
  scripted module. With opentide #1742 (`3213bb17`) and #83 @ `881ad91`, `run_query`, `validate_query` live and
  `deploy_rule` (`dry_run:false`) all reach the local fake tenant, forged answers are dropped and stdout stays clean
  ("Rerun" section).
- **Kiro: the extension runs** (tier 4, serve and the language server answer) **but the opentide MCP server does not
  reach Kiro's agent.** On #83 the extension takes the VS Code provider path because Kiro's Code OSS core has that API;
  Kiro's own agent does not use it and the extension then writes no `~/.kiro/settings/mcp.json`. Everything inside
  Kiro's UI (editor screenshots, its MCP panel) is behind a mandatory sign-in I do not have.

## Code review of #82 and #83

Read against SPEC §4/§12, CONTRACTS, and VS Code's extension guidelines. Items that became issues are marked.

- **Trust**: good. `decideNow` returns `provide: false` in Restricted Mode before reading any setting or file
  (`src/features/agents/index.ts`); `package.json` `untrustedWorkspaces.restrictedConfigurations` lists
  `opentide.mcp.provide`, `opentide.envFile`; `opentide.wasi.enabled` is documented as ignored in Restricted Mode and was.
  Observed: no `launcher`, no MCP server, no config file in an untrusted folder. The Restricted-Mode log line is
  misleading (issue D, #90).
- **Path mapping** (`src/core/wasi/paths.ts`): host and guest paths are rewritten by a regular expression over *every
  string of every JSON message*, not only the fields that are paths. On POSIX with the launcher, guest = host, so
  nothing changes (verified). Under `@vscode/wasm-wasi` the guest is `/workspace` or `/workspaces/<name>`: a rule
  description or a query that contains the text `/workspace/...` would be rewritten to a host path on the way out.
  Not reproduced (`/workspace` did not occur in my objects) and not filed; worth a test with a rule that mentions the
  path. Two multi-root folders with the same *name* map to the same `/workspaces/<name>` under `@vscode/wasm-wasi`
  unless `root.toWasm` disambiguates (`src/core/services/wasi.ts:153` falls back to `guestPathOf`); not tested
  (my two folders had different names).
- **Process lifetime**: good. The launcher processes die with the window on both exits I tried (graceful close, SIGKILL of the main
  process). The bridge parent and its launcher child both go.
- **Environment**: the extension-host `serve` path forwards only `OPENTIDE_*`, proxy variables, `NO_COLOR` and `TZ`
  (`src/core/wasi/env.ts`), but `launcher.cjs` `moduleEnv()` hands the module **the whole environment** of its
  process (everything but `ELECTRON_RUN_AS_NODE`). For MCP, terminal and tasks that is how credentials reach the
  module, so it is probably intended; it differs from the stated "it sees only what it is given" (`env.ts` comment).
  Not filed.
- **Error messages**: `workspace_not_found: … Set OPENTIDE_REPO_ROOT … in the host's MCP server settings` is
  actionable. `needs $X, which is not set` is wrong when `opentide.envFile` provides it (issue B, #88). The notification
  text `$(pass) …` is literal (issue C, #89).
- **Size budget** (`pins.json` `vsix`): #82's artifact is 13,952,463 bytes (13.3 MiB); #83's build 13,959,058 bytes
  (13.3 MiB, `mcp-wasi.js` adds 9 KB): under the 15 MiB target and the 20 MiB budget (`size.json`: `withinTarget: true`).
  Installed size 52.4 MiB. The module is 26.9 MiB of that; each of the engine and the module compiles a few hundred ms
  at start (`compiled … in 428 ms`).
- **Licence files**: `dist/wasi/` ships `LICENSE` (EUPL-1.2) and `NOTICE`, and `dist/engine/` ships the rc.2 engine's
  `THIRD-PARTY-LICENSES.html` and `licenses/wasi-libc/`. I extracted the crate names embedded in the module (130,
  from its `registry/src/…` paths): all 130 appear in that HTML, so nothing is missing *for this module*; but the
  list belongs to a different build (rc.2 engine, pinned separately in `pins.json`), sits in another directory and
  would silently go stale when the module is bumped (issue J, #92).
- **Documentation** (issue E, #91): the activation log line, `opentide.wasi.enabled`'s description and the PR text say
  "every command works" and MCP needs no install; tenant MCP tools do not work on #82, and on #83 not yet either.
- **#83, host detection** (issue F, #84): `hasProviderApi` is decided by the existence of
  `lm.registerMcpServerDefinitionProvider` and `McpStdioServerDefinition` (`src/features/agents/index.ts:80-92`).
  Kiro inherits both from Code OSS, so the user-level-file fallback is unreachable there. The comment in the code
  ("and Kiro if it implements it") assumes that implementing the API means the host's agent uses it.
- **#83, user-level entries** (issue G, #86): `entryOf` drops `OPENTIDE_REPO_ROOT` (`index.ts`, "without the per-folder
  variable") and `forkTarget(...).workspaceVariable` is `false` for all three editors, so the entry depends on the
  agent's spawn cwd.
- **#83, writer**: correct on every case I ran (new file, idempotent rewrite, comments refused, foreign `opentide`
  entry kept, other servers and top-level keys kept, removal only of the marked entry). The path `~/.kiro/settings/mcp.json`
  matches where `kiro.kiro-agent` reads its user MCP file.
- **#83, bridge**: filter and delegation behave as documented; stdout is clean even with non-JSON noise from the module
  (it goes to stderr). `process.stdin.pipe(child.stdin)` forwards every editor line to the module unfiltered,
  including a line whose `method` starts with `opentide/` (the private link): only the module → editor direction is
  filtered. Low risk (the editor is trusted), not filed.
